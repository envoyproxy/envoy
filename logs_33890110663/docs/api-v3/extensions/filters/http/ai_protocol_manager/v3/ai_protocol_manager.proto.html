AI Protocol Manager (proto)

This extension has the qualified name envoy.filters.http.ai_protocol_manager

Note

This extension is functional but has not had substantial production burn time, use only with this caveat.

This extension has an unknown security posture and should only be used in deployments where both the downstream and upstream are trusted.

Tip

This extension extends and can be used with the following extension categories:

  • envoy.filters.http

  • envoy.filters.http.upstream

This extension must be configured with one of the following type URLs:

  • type.googleapis.com/envoy.extensions.filters.http.ai_protocol_manager.v3.AiProtocolManager

  • type.googleapis.com/envoy.extensions.filters.http.ai_protocol_manager.v3.AiProtocolManagerPerRoute

Warning

This API feature is currently work-in-progress. API features marked as work-in-progress are not considered stable, are not covered by the threat model, are not supported by the security team, and are subject to breaking changes. Do not use this feature without understanding each of the previous points.

AI Protocol Manager filter configuration overview.

extensions.filters.http.ai_protocol_manager.v3.AiProtocolManager

[extensions.filters.http.ai_protocol_manager.v3.AiProtocolManager proto]

Configuration for the AI Protocol Manager filter.

The filter manages AI endpoint traffic on both directions of a stream. On the request path it holds a declared AI endpoint’s payload and parses it, which is what lets routing, admission and policy act on a payload the proxy understands rather than on opaque bytes. On the response path it can extract normalized LLM token usage into dynamic metadata.

Request and response processing are independently enabled by the presence of request_handling and response_handling. Which routes are AI endpoints — and which wire API each speaks — is declared with the per-route configuration.

{
  "request_handling": {...},
  "response_handling": {...}
}
request_handling

(extensions.filters.http.ai_protocol_manager.v3.RequestHandling) Request-side AI protocol processing. When unset, the decode path is a pure passthrough — including on routes carrying per-route configuration.

response_handling

(extensions.filters.http.ai_protocol_manager.v3.ResponseHandling) Response-side AI protocol processing. When unset, the encode path is a pure passthrough.

extensions.filters.http.ai_protocol_manager.v3.RequestHandling

[extensions.filters.http.ai_protocol_manager.v3.RequestHandling proto]

Request-side processing configuration. A route that carries a per-route request declaration has its payload held, offloaded, and parsed strictly: a body that is not well-formed JSON is rejected with a 400 rather than forwarded for the upstream to interpret differently.

{
  "parse_unconfigured_routes": ...,
  "limits": {...}
}
parse_unconfigured_routes

(bool) Attempt best-effort JSON parsing on routes without a per-route configuration.

Defaults to false: unconfigured routes are not buffered or parsed. When true, such routes are parsed too, but never failed over it — a route that declared no AI wire contract has nothing to hold its payload to, so a body that fails to parse is forwarded unchanged.

Only requests that can be held to end of stream are taken: the request must carry a JSON content type (application/json or a +json suffix) and must not be gRPC or Connect streaming, an upgrade, or a CONNECT. Holding a full-duplex request would stall it, since the client may not finish the request until it sees a response the held upstream cannot produce.

limits

(extensions.filters.http.ai_protocol_manager.v3.RequestParsingLimits) Request-path parsing limits. Defaults apply when unset.

extensions.filters.http.ai_protocol_manager.v3.RequestParsingLimits

[extensions.filters.http.ai_protocol_manager.v3.RequestParsingLimits proto]

Per-stream limits for request payload parsing.

{
  "inline_string_threshold_bytes": {...}
}
inline_string_threshold_bytes

(UInt32Value) Maximum size, in bytes, of a decoded string value kept inline in the parsed document; a larger value stays in the external buffer and is referenced by offset. Object keys are always inline.

This is the deployment-wide default, applied when a declared API’s payload schema does not pin its own threshold. Defaults to 1KiB, which keeps ordinary metadata (model names, roles, tool names) inline while conversation content goes to the buffer.

Keep it above the longest model name in use. Values over the threshold are offloaded, and on a declared AI endpoint the payload schema requires model inline, so an offloaded one is rejected with a 400.

extensions.filters.http.ai_protocol_manager.v3.ResponseHandling

[extensions.filters.http.ai_protocol_manager.v3.ResponseHandling proto]

Response-side processing configuration. Individual response features are enabled by the presence of their corresponding messages.

{
  "token_usage": {...}
}
token_usage

(extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtraction) Extract canonical token usage from eligible AI responses. When unset, token usage extraction is disabled.

extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtraction

[extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtraction proto]

Configuration for canonical response token-usage extraction.

Eligible 2xx SSE and JSON responses are observed as they stream through; the filter never stops iteration or modifies the response, and no extraction failure can affect it. The result is published at a clean end of stream under one namespace as typed dynamic metadata: the authoritative record is envoy.data.ai.v3.TokenUsage, consumable through typed metadata readers such as ext_proc typed forwarding. No untyped Struct mirror is emitted.

{
  "include_unconfigured_routes": ...,
  "default_api_protocol": ...,
  "metadata_namespace": ...,
  "limits": {...}
}
include_unconfigured_routes

(bool) Also inspect responses on routes without per-route configuration.

Defaults to false: only routes carrying an AiProtocolManagerPerRoute configuration are inspected, so enabling token usage on a mixed listener does not silently parse unrelated JSON/SSE responses. Enable this for response-only installations whose routes cannot be declared — for example an upstream installation on a dynamic-forward-proxy cluster.

default_api_protocol

(type.ai.v3.ApiProtocol) Fallback wire API used when the route does not identify a response API.

API_PROTOCOL_UNSPECIFIED means auto-detect from the response shape (only strongly shaped, value-validated markers lock a stream). This is a fallback, not an override of per-route response configuration; see the per-route configuration for the full precedence.

metadata_namespace

(string) Namespace for the emitted typed dynamic metadata. Defaults to envoy.ai.token_usage.

limits

(extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtractionLimits) Extraction resource limits. Defaults apply when unset.

extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtractionLimits

[extensions.filters.http.ai_protocol_manager.v3.TokenUsageExtractionLimits proto]

Per-stream memory and work limits for token-usage extraction. The response itself always streams through unaffected; on any limit only extraction state is dropped and the published record is flagged.

{
  "max_sse_event_size": {...},
  "max_json_body_size": {...},
  "max_parsed_sse_events": {...}
}
max_sse_event_size

(UInt32Value) Maximum size of one SSE event inspected for token usage. This is a hard bound on retained extraction state, regardless of how large individual data frames are: a pending event over the cap is discarded through its real terminating blank line, and a complete event over the cap is skipped without parsing.

Defaults to 1MiB: OpenAI Responses API streams carry usage on terminal lifecycle events that embed the complete response object, so ordinary long generations produce usage-bearing events far larger than typical SSE deltas. Lower this in constrained deployments at the cost of losing usage from long generations.

max_json_body_size

(UInt32Value) Maximum JSON response body inspected for token usage. A larger body — including one whose content-length already exceeds the cap — is not inspected. Defaults to 4MiB.

max_parsed_sse_events

(UInt32Value) Maximum number of SSE payloads parsed as JSON for one response, counting malformed payloads; events skipped by name (keepalives, content deltas) do not count. max_sse_event_size bounds one event; this bounds the parse work a long-lived stream can extract from the worker. On exhaustion the accumulated usage is kept and published as partial, and extraction goes inert.

Defaults to 65536 — far above ordinary streams. Raise it for extremely long generations whose every chunk must be parsed (OpenAI Chat Completions streams, whose chunks are unnamed and cannot be skipped by classification).

extensions.filters.http.ai_protocol_manager.v3.AiProtocolManagerPerRoute

[extensions.filters.http.ai_protocol_manager.v3.AiProtocolManagerPerRoute proto]

Per-route configuration. Its presence declares the route an AI endpoint.

Request and response wire protocols are declared separately because protocol translation can make the client-facing request API differ from the provider’s response API. For response token-usage extraction the effective wire API is resolved in precedence order: per-route response.api_protocol, then per-route request.api_protocol, then default_api_protocol, then auto-detection.

{
  "request": {...},
  "response": {...}
}
request

(extensions.filters.http.ai_protocol_manager.v3.RequestPerRoute) Request-side route configuration. Its presence hands the request payload to the filter to hold and validate (when request_handling is enabled).

response

(extensions.filters.http.ai_protocol_manager.v3.ResponsePerRoute) Optional response-side route configuration. When absent, response processing inherits request.api_protocol when available, then the global fallback.

extensions.filters.http.ai_protocol_manager.v3.RequestPerRoute

[extensions.filters.http.ai_protocol_manager.v3.RequestPerRoute proto]

Per-route request-side behavior.

{
  "api_protocol": ...
}
api_protocol

(type.ai.v3.ApiProtocol) The wire API a request payload on this route follows. API_PROTOCOL_UNSPECIFIED declares the endpoint without naming its API.

Payloads are validated against the declared API’s schema when one is defined (currently OpenAI Chat Completions); a schema-invalid payload is rejected with a 400.

extensions.filters.http.ai_protocol_manager.v3.ResponsePerRoute

[extensions.filters.http.ai_protocol_manager.v3.ResponsePerRoute proto]

Per-route response-side behavior.

{
  "api_protocol": ...
}
api_protocol

(type.ai.v3.ApiProtocol) The wire API the response on this route follows. This can differ from request.api_protocol when the gateway performs protocol translation. API_PROTOCOL_UNSPECIFIED falls through the precedence chain above.
