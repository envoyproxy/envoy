# Choosing tarballs

Where the dependency maintainer provides a tarball, prefer that over the
automatically generated Github tarball. Github generated tarball SHA256
values can change when Github change their tar/gzip libraries breaking
builds. Maintainer provided tarballs are more stable and the maintainer
can provide the SHA256.

# Adding external dependencies to Envoy (C++)

## Native Bazel

This is the preferred style of adding dependencies that use Bazel for their
build process.

1. Add a `bazel_dep` for the module in [`MODULE.bazel`](../MODULE.bazel) and
   add or update its registry entry.
2. Reference your new external dependency in some `envoy_cc_library` via the
   `deps` attribute.
3. `bazel test //test/...`

## External CMake (preferred)

This is the preferred style of adding dependencies that use CMake for their build system.

1. Add a `bazel_dep` for the module in [`MODULE.bazel`](../MODULE.bazel) and add or update its
   entry in the [Envoy Bazel registry](https://github.com/envoyproxy/bazel-registry). The registry
   entry supplies the `BUILD` overlay that drives the CMake build via `envoy_cmake` (defined in
   [`bazel/envoy_build_system.bzl`](envoy_build_system.bzl)).
2. Reference your new external dependency in some `envoy_cc_library` via the `deps` attribute.
3. `bazel test //test/...`

# Adding external dependencies to Envoy (Python)

Python dependencies should be added via `pip` and `rules_python`. The process
is:

1. Add the package to the relevant `requirements.txt` (for example
   [`tools/base/requirements.txt`](../tools/base/requirements.txt)), which is consumed by the
   `pip_parse()` calls in [`bazel/python_dependencies.bzl`](python_dependencies.bzl). To create a
   new set of requirements from scratch, see [`tools/README.md`](../tools/README.md).

2. Add a `requirements("<package name>")` in the `BUILD` file that depends on
   this package.

You can use [`tools/config_validation/BUILD`](../tools/config_validation/BUILD) as an example
for this flow. See also the [`rules_python`](https://github.com/bazelbuild/rules_python)
documentation for further references.

# Updating an external dependency version

1. Update the corresponding `bazel_dep` in [`MODULE.bazel`](../MODULE.bazel) and
   the module in the Envoy Bazel registry.
2. Once the registry change has landed, re-pin the registry commit and regenerate the lockfiles
   with `ci/do_ci.sh registry` (see [`ci/README.md`](../ci/README.md)).
3. Update the corresponding metadata in [`bazel/deps.yaml`](deps.yaml).
4. `bazel test //test/...`

# Overriding an external dependency temporarily

A dependency provided as a Bazel module can be pointed at a local copy with
[`--override_module`](https://bazel.build/reference/command-line-reference),
e.g. `--override_module=boringssl=/path/to/boringssl`. The name of the dependency is the module
name used in its `bazel_dep` in [`MODULE.bazel`](../MODULE.bazel). The option can be used multiple
times to override multiple dependencies. The path of the local copy has to be an absolute path.

Repositories that are not modules -- i.e. those generated by a module extension -- must instead be
overridden with
[`--override_repository`](https://bazel.build/reference/command-line-reference)
using their *canonical* (mangled) repository name rather than their apparent name. See
[`ci/mac_ci_steps.sh`](../ci/mac_ci_steps.sh) for a worked example.

For modules whose registry overlay builds them with `envoy_cmake()`, it is necessary to populate
the local copy with some additional Bazel machinery to support overriding:
1. Place a `BUILD` file with `filegroup(name = "all", srcs = glob(["**"]), visibility = ["//visibility:public"])`
   in the root.

# Debugging external dependencies

For all external dependencies, overriding with a local copy as described in the
previous section is a useful tool.

Below we describe specific tips for obtaining additional debug for specific
dependencies:

* `libevent`: add `"EVENT__ENABLE_VERBOSE_DEBUG": "on",` to the `cache_entries` of the
  `envoy_cmake()` target in the `libevent` module's `BUILD` overlay in the
  [Envoy Bazel registry](https://github.com/envoyproxy/bazel-registry), for verbose tracing of
  libevent processing.

* `nghttp2`: set `ENVOY_NGHTTP2_TRACE` in the environment and run at `-l trace`.

* `QUICHE`: set `ENVOY_QUICHE_VERBOSITY=n` in the environment to display
  verbose logs up to level `n`.

# Distdir - prefetching dependencies

Usually Bazel downloads all dependencies during build time. But there is a
possibility to prefetch dependencies and point Bazel to them by using `--distdir`
option and providing a path to directory which contains tarballs with exactly
the same name and the same SHA256 sum that are defined by the registry module.

For example, let's assume that your distdir location is `$HOME/envoy_distdir`.
To prefetch `boringssl`, use the archive that the registry selects for the version pinned in
[`MODULE.bazel`](../MODULE.bazel):

```
 bazel_dep(name = "boringssl", version = "<version from MODULE.bazel>")
```

`$HOME/envoy_distdir` needs to contain that archive, named exactly as the registry's
`source.json` records it.

Then Envoy needs to be built with the following command:

```
bazel build --distdir=$HOME/envoy_distdir //source/exe:envoy
```
